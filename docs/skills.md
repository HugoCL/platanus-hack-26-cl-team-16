# Skills

Generated by `node scripts/skills/check.mjs --write` from `scripts/skills/sources.json` and `skills-lock.json`. Do not edit by hand.

Repo skills live in `.agents/skills/<name>/SKILL.md`, which Capy reads. Pick one with `$` followed by the name. Install or refresh them with `pnpm skills:sync`, and validate with `pnpm skills:check`.

## Limitations

### Toolbox (first-party)

Selection:

- Written and edited in place under `.agents/skills/<name>/`. `pnpm skills:sync` never touches these folders, they are not in `skills-lock.json` and they get no content hash check. `pnpm skills:check` still validates their frontmatter (`name` matches the folder, `description` is not empty).

Limitations:

None recorded.

### gstack (Capy wrapper only)

Selection:

- Only the Capy wrapper (`capy/skill/gstack/`: SKILL.md, captain.md, factory.md, lane-card.md, scripts/install.sh) is vendored. gstack's other 62 workflow skills are not copied into the repo; the wrapper installs them on the thread's own machine.

Limitations:

- `gstack`: `scripts/install.sh` clones gstack to `~/.local/share/gstack`, installs a SHA-256 verified Bun plus a `~/.local/bin/bun` shim, and runs gstack's own setup for the Claude Code and Codex hosts. The workflows (`/autoplan`, `/ship`, `/review`, `/qa`) therefore land in the machine home (`~/.claude/skills`, `${CODEX_HOME:-$HOME/.codex}/skills/gstack-*`), never under `.agents/skills/`. It is meant for Capy's Ubuntu VMs, so do not run it on a laptop.
- `gstack`: the skill refuses to run a workflow until `bash scripts/install.sh --check` prints a `gstack: ok` trailer in the same session. With no checkout the trailer is `gstack: fail not-installed`, and `bash scripts/install.sh --for <skill>` must run first on each machine (about 30 s cold).
- `gstack` (`captain.md`, `factory.md`, `lane-card.md`): these describe Capy crew rules (CREW.md, the READY contract, `GSTACK_CAPY=1`) and point to files that live in the gstack checkout (`crew/docs/captain.md`, `capy/README.md`), not in this repo. `lane-card.md` and `SKILL.md` keep scratch under `~/.capy/work/<name>`.
- `gstack`: upstream designs this folder to be copied into the owner's Capy Drive. `SKILL.md` reports `CAPY_WRAPPER_STALE` when it is older than the checkout expects. Refresh it with `pnpm skills:sync --update`.
- `gstack`: the vendored wrapper is pinned, but the gstack runtime that `.capy/setup.json` clones (`~/.local/share/gstack`) tracks upstream `main` and updates itself. Pinning only the clone does not hold: `scripts/install.sh` fast-forwards a clean, unpinned checkout that is below the supported minimum (read from origin's `capy/support.env`), and the checkout's own session script can upgrade it. The pin options the vendored `install.sh` documents are `--revision <ref>` (clone at that ref; a pinned checkout below the minimum fails with `REVISION_BELOW_MINIMUM`), `GSTACK_CAPY_AUTO_UPGRADE=0` (no fast-forward; above the floor the checkout's session overrides it once it is 24 hours behind, unless `GSTACK_PIN_REASON` is set) and `GSTACK_UPDATE_CHANNEL=stable` (follow the tagged release instead of every merge on `main`). The repo's initialize script uses none of them, and its install step rejects a detached or pinned checkout, so it does not pin the clone.

### pstack (Claude Code tree)

Extra files copied alongside the skills:

- `harness/pstack/claude-code/docs/harness/claude-code.md` to `.agents/docs/harness/claude-code.md`
- `harness/pstack/claude-code/agents` to `.agents/agents`

Selection:

- All 58 skills of the generated Claude Code tree (`harness/pstack/claude-code`) of `cursor/plugins`. The Cursor-native tree and the finografic port are not used. This is not the hand-edited `poteto-mode` in `~/.claude/skills`.
- `docs/harness/claude-code.md` is copied to `.agents/docs/harness/` so the link `../../docs/harness/claude-code.md` in `poteto-mode/SKILL.md` resolves. The two custom agents go to `.agents/agents/`.

Limitations:

- `poteto-mode` and `poteto-help` spawn `poteto-agent` subagents (the adapter names it `pstack:poteto-agent`). The definition (`.agents/agents/poteto-agent.md`, `model: claude-opus-5-5-xhigh-fast`) is a Claude Code custom-agent file. Capy documents only skills folders, so it is not registered there (UNCONFIRMED how a Capy thread resolves the name). Claude Code resolves `pstack:poteto-agent` and `pstack:comment-sicko` only with the pstack plugin installed: with `pnpm skills:link` alone, translate the definition into a native `Agent` call (brief, model and effort), as `$harness-map` describes. `.agents/agents/` is also where Antigravity looks for custom agents, but these files are in Claude Code format, so do not expect them to work there as they are.
- `poteto-mode`, its playbooks (`shipping`, `opening-a-pr`, `autopilot-full`) and `poteto-help` name `deslop`, `control-ui` and `control-cli` from Cursor's `cursor-team-kit` plugin. Those three are vendored in the `cursor-team-kit` collection of this repo, so the names resolve. The rest of `cursor-team-kit` is not vendored.
- Subagent steps (`how`, `no-comments`, `swarm`, `arena`, `poteto-mode`) are written for Cursor's `Task` tool. `.agents/docs/harness/claude-code.md` maps them to Claude Code; there is no mapping for Codex or Capy, so use the harness's own subagent tool, or do the step inline.
- `poteto-help` links the pstack README and `docs/guide/*.md` (`../../README.md`, `../../docs/guide/01-setup.md`, ...). Those files are not vendored, so the links are dead here. Read them on the upstream repo.
- `setup-pstack` writes `~/.cursor/rules/pstack-models.mdc` (a Cursor user path outside the repo). Do not run it on a Capy thread.
- `poteto-mode/scripts/` (`watch-pr`, `bootstrap.ts`, `package.json`, `bun.lock`) needs Bun, and `statechart/scripts/statechart` needs Node 22.18 or newer, or Bun 1.1.15 or newer.
- 57 of the 58 skills set `disable-model-invocation: true`, a Claude Code frontmatter key. Invoke them by name with `$`. How Capy treats that key is not documented.
- `poteto-mode` tells the agent to read the Claude Code adapter (`.agents/docs/harness/claude-code.md`), which maps Cursor tool names to Claude Code names (`Task` to `Agent`, `AskQuestion` to `AskUserQuestion`). It is written for Claude Code, so the mapping only holds on Claude models.

### Cursor Team Kit

Selection:

- Five of the 18 skills of the `cursor-team-kit` plugin in `cursor/plugins` (`cursor-team-kit/skills/`): `thermo-nuclear-code-quality-review`, `make-pr-easy-to-review`, `deslop`, `control-ui` and `control-cli`. They are the ones `pstack` points at (`deslop`, `control-ui`, `control-cli`) plus the two review and PR-hygiene skills. The plugin's other skills, its agents (`agents/thermo-nuclear-code-quality-review.md`), rules and assets are not vendored.

Limitations:

- `thermo-nuclear-code-quality-review` sets `disable-model-invocation: true`, a Claude Code frontmatter key, so invoke it by name with `$thermo-nuclear-code-quality-review`. How Capy treats that key is not documented. Upstream also ships a subagent definition for it (`agents/thermo-nuclear-code-quality-review.md`) that is not vendored, so it runs as a plain skill in the current thread. It is deliberately harsh: it treats a file growing past 1000 lines and any new ad-hoc branching as presumptive blockers.
- `make-pr-easy-to-review` can rewrite history and force-push a PR branch. It tells the agent to propose a plan first and to rewrite only when the user agrees, but this repo's rule that merging and pushing needs a human still applies. It needs an authenticated `gh` and a PR to work on.
- `deslop` diffs the branch against `main` and edits the files in place. It has no extra files and no tool requirements.
- `control-ui` builds or adapts a local browser harness (Playwright by default, Chromium remote debugging for Electron). It refers to a `verify-this` skill that is not vendored, writes screenshots to `/tmp`, and needs a browser: `pnpm smoke` already provides Playwright and Chromium, and `agent-browser` is the other browser tool in this repo.
- `control-cli` drives interactive CLIs and TUIs through `tmux`, a PTY script (Python, Node or Expect) and the Node inspector, none of which this repo installs. `tmux` has to be on the machine, and asciinema is only mentioned as optional.
- Each of the five is a single `SKILL.md` with no scripts or references. They are written for Cursor's agent but name no Cursor-only tool or path.

### tstack

Limitations:

- `council` and `sol-loop` use T3 Code's `orchestrator_capabilities` and `delegate_task` to reach other providers' models. Elsewhere `council` uses the harness's own subagents and reports a failure when three providers are not reachable, and `sol-loop` needs a Sol subagent or reports the blocker.
- `babysit-pr` uses T3 Code's `watch_pull_request`, and falls back to `scripts/pr-wait` everywhere else. `pr-wait` needs Python 3 and an authenticated `gh`. `full-send` and `full-stop` also call `watch_pull_request` and `unwatch_pull_request` when running in T3 Code.
- `full-send` and `full-stop` ship `agents/openai.yaml` Codex agent metadata. Capy ignores it.

### Ponytail (skills only)

Selection:

- Only the six skills (`ponytail`, `ponytail-review`, `ponytail-audit`, `ponytail-debt`, `ponytail-gain`, `ponytail-help`). No lifecycle hooks, status line, band, or root AGENTS.md rules are installed.

Limitations:

- `ponytail-help` documents `/ponytail band` as a Claude Code feature (the Band section). Without the hooks it is not installed here, so those commands do nothing.
- `ponytail-gain` reports figures from a headless Claude benchmark of Ponytail 5. They are not measurements of this repo.
- Upstream also ships always-on rules (AGENTS.md, `.agents/rules/ponytail.md`) that are not copied. Ponytail only runs when you invoke a `$ponytail*` skill.

### Anthropic skills

Limitations:

- `webapp-testing`: its scripts and examples use the Python `playwright` package (`from playwright.sync_api import sync_playwright`) and Chromium. `SKILL.md` declares no install step, so Python 3 plus `pip install playwright && python -m playwright install chromium` must come from the repo setup. `scripts/with_server.py` itself uses only the Python standard library.
- `frontend-design` steers away from a cream background, serif display type and a terracotta accent, which it calls common tells. The rules are Anthropic's and are vendored unchanged.
- Each skill ships its own `LICENSE.txt` (Apache-2.0). Upstream has no root LICENSE, so `licenses/anthropic-skills.txt` is a copy of `skills/frontend-design/LICENSE.txt`.

### Matt Pocock skills

Limitations:

- `to-tickets` sets `disable-model-invocation: true`, so invoke it explicitly with `$to-tickets`.
- `to-tickets` reads the tracker config written by `/setup-matt-pocock-skills`. That setup skill is not vendored. `docs/agents/issue-tracker.md` (local markdown, tickets under `.scratch/<feature-slug>/issues/`) and `docs/agents/domain.md` are the files it would have written. `triage` is not installed, so there is no `docs/agents/triage-labels.md`; the tracker file lists plain `Status:` values instead.
- The setup skill also writes an `## Agent skills` block into AGENTS.md or CLAUDE.md. That block is not written here.

### Vercel AI SDK

### Vercel UI SDK

Selection:

- Pinned to the commit tagged `@ui-sdk/core@0.1.0-beta.7` and `@ui-sdk/react@0.1.0-beta.7`, the versions in `package.json`. To bump, change the commit in `source` to the new release tag's commit together with the packages, then run `pnpm skills:sync ui-sdk` (`--update` does not move a commit pinned in `source`).

Limitations:

- `ui-sdk` reads the docs bundled in the installed packages (`node_modules/@ui-sdk/react/docs/llms.txt`, `core.md`, `rendering.md`). It does nothing useful without `@ui-sdk/react` and `@ui-sdk/core` installed.
- UI SDK is in beta (0.1.0-beta.x). Its APIs and the skill can change between betas.
- `ui-sdk` says every task gets tests, including an agent test with `createAgent`, and its `testing.md` assumes a unit runner (jsdom). This repo has no unit test runner, only `pnpm smoke` (Playwright).
- `ui-sdk` writes install commands with `npm`/`npx`. This repo is pnpm only: use `pnpm add`, and never weaken `minimumReleaseAge` to get a newer beta.
- `ui-sdk` tells the agent to run `npx tsc --noEmit`. Here that is `pnpm typecheck`.

### agent-browser

Limitations:

- `agent-browser` is a discovery stub (`hidden: true`, `allowed-tools: Bash(agent-browser:*)`). The real instructions come from the installed CLI (`agent-browser skills get core`), so the skill is useless until the `agent-browser` CLI is installed and `agent-browser install` has downloaded Chrome for Testing (to `~/.agent-browser/browsers`).
- Its description says to prefer `agent-browser` over any built-in browser automation or web tools, which competes with whatever browser tool the harness already provides.

### agent-desktop (computer use)

Selection:

- Only the macOS and Linux skills. `agent-desktop-windows` and `agent-desktop-ffi` are not vendored. There is no upstream skill named `agent-desktop`, so the README's `--skill agent-desktop` command finds nothing.

Limitations:

- Both skills defer to the `agent-desktop` CLI for the core loop (`agent-desktop skills get desktop`), so the CLI must be installed on the machine.
- `agent-desktop-macos` needs the macOS Accessibility grant for the launching app (`agent-desktop permissions --guide`), and Screen Recording for screenshots.
- `agent-desktop-linux` needs Ubuntu 24.04+, a graphical session of the signed-in user and a running AT-SPI bus. A TTY login, an SSH shell without session variables or a container without a bus does not work. Whether a Capy cloud VM provides this is UNCONFIRMED.

### Convex agent skills

Selection:

- Installed (13): `convex` (router), `convex-design`, `convex-expert`, `convex-docs` (build and look up Convex code), `convex-env`, `convex-seed`, `convex-crons`, `convex-agent` (env vars, seed data, scheduled jobs, AI agent backends in a hackathon app), `convex-test`, `convex-verify`, `convex-reviewer`, `convex-authz` (tests and security review), `convex-deploy-guard` (consent before touching prod).
- Left out: `convex-auth` (Convex Auth, the app uses Clerk), `convex-quickstart` (the repo already ships the Next.js scaffold), `convex-add` (fetches its procedures from a remote catalog), `convex-billing`, `convex-domains`, `convex-create-component`, and the production operations set (`convex-migrate`, `convex-migrate-rehearse`, `convex-monitor`, `convex-sentinel`, `convex-self-heal`, `convex-insights`, `convex-advisor`, `convex-cost`, `convex-backup`, `convex-launch-readiness`, `convex-optimize`, `convex-explain-app`, `convex-suggest`, `convex-improve-convex-plugin`).

Limitations:

- `convex` is a router that points at skills which are not installed (`convex-add`, `convex-quickstart`, `convex-auth`, `convex-monitor`, `convex-sentinel`, `convex-self-heal`, `convex-migrate`, `convex-cost`). Ignore those routes. Note that its route 2 sends new apps to `convex-quickstart`; this repo already has its scaffold.
- `convex` route 3 tells the agent to fetch `https://basic-anteater-667.convex.site/capabilities.json?src=agent-skills` and follow the served `/capability/<id>.md` docs, and to prefer the served copy over the bundled one. That is remote instructions executed at run time. It is only reachable through `convex-add`, which is not installed, but the router text remains.
- `convex-docs` fetches version-current Convex docs at run time (page-as-markdown or the `search_convex_docs` MCP tool when available). `convex-deploy-guard` and `convex-docs` reference the official Convex MCP server, which this repo does not configure.
- `convex-expert` and `convex-design` end with a self-verify rule that runs `CONVEX_AGENT_MODE=anonymous npx convex dev --once` when `npx convex whoami` fails. `CONVEX_AGENT_MODE=anonymous` is used by `pnpm dev` and verified with convex 1.50.0.
- `convex-design` says to delegate `convex/` code to "the convex-expert subagent". Here `convex-expert` is installed as a skill, not a subagent.
- The upstream README is stale. It lists skills that are not in the tree (for example `convex-setup-auth`), and `convex/SKILL.md` and `convex-quickstart/SKILL.md` are generated files. The skills CLI records the source as `convex/agent-skills`, not `get-convex/agent-skills`.

### Clerk skills

Selection:

- Installed (7 of 21): `clerk`, `clerk-setup`, `clerk-nextjs-patterns`, `clerk-cli`, `clerk-webhooks`, `clerk-testing`, `clerk-orgs`. The other framework, mobile, migration, billing, custom-UI and backend-API skills do not apply to a Next.js template.

Limitations:

- Upstream `clerk/skills` has no LICENSE file. Its README, `plugin.json` and each skill's frontmatter state MIT. `licenses/clerk.txt` is the MIT text from `clerk/javascript`, Clerk's own repository, pinned in `sources.json`.
- `clerk` is a router that mentions skills which are not installed (`clerk-migrate`, `clerk-billing`, `clerk-custom-ui`, `clerk-react-patterns`, `clerk-backend-api`).
- `clerk-setup`, `clerk-nextjs-patterns`, `clerk-orgs`, `clerk-webhooks` and `clerk-testing` set `allowed-tools: WebFetch`, a Claude-style frontmatter key, and link to clerk.com docs that the agent is expected to fetch.
- `clerk-setup` runs `npx -y clerk@latest init` (accountless setup that writes keys to `.env.local`) and needs Node 20.9.0 or newer. `clerk-cli` also accepts `pnpm dlx clerk@latest`. `clerk-cli/references/agent-mode.md` warns that home-directory config, the OS keychain and outbound Clerk requests may be blocked in a sandbox, so auth or link errors then need a rerun on the host.
